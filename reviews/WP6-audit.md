# WP6 audit: full dry run of the 120-minute workshop, `main` at `1b2dfea`

Scope: I played the **facilitator** (blocks 1-10, following `demo/FACILITATOR.md`, `demo/hook_demo.ipynb`, then the notebook) and a **participant with no ML background** (`audio_workshop.ipynb` from `workshop_files.zip` in an empty folder: unsolved, with typical mistakes, solved). Goal I judged against, in Asy's words: "smooth, accurate, and can demonstrate all the concepts clearly eg RNN, LSTMs".

Short verdict: the machinery is sound: it runs end to end from the zips with no errors (unsolved 99 s, solved 92 s, mistaken 91 s on CPU), the numbers are honest, and nothing needs a model, training or `prototype/` change. What is missing is **clarity of the teaching moments** and **a written run-sheet**. The hook is smooth if everything goes right and has no soft landing if it does not. Nothing below is a correctness bug in the model, and every fix is inside `demo/` and `notebook/`. Three findings are blockers for "demonstrate the concepts clearly" (F1, F2, F3); the rest are should-fix or polish.

Top five (details below):
1. **F1** Block 4 "break the memory": following cell 29 literally gives a failing check and no contrast.
2. **F2** Gates are only described, never shown, and the LSTM story contradicts Part B's own numbers at knob 0.
3. **F3** No run-sheet for blocks 2-10, no written plan for how participants get the notebook and zip, or when they run setup.
4. **F4** Block 9's default example cannot answer "which earlier line should it have remembered?".
5. **F5** Hook: the backup recording is never played to the room, and a CPU-only Colab turns "one button" into a 3-minute wait.

## Hook day: clicks, waits, single points of failure

Live path, as the notebook is written: before the session (1) open `hook_demo.ipynb` in Colab (the page does not say how; the repo is private), (2) Runtime > Change runtime type > T4 > Save (the VM restarts), (3) upload `facilitator_files.zip`, (4) run cell 2 and wait (pip install, the `medium.en` download of about 1.5 GB and the load: my estimate is a few minutes on Colab, not measured here). During the hook: (5) run the recorder cell, click Allow on the microphone prompt, (6) the skit, (7) click in the input box and press Enter, (8) wait a few seconds for upload and ffmpeg, (9) run the button cell, wait. That is **three clicks plus the Enter during the hook**, not "one button"; the "one button" is the press at step 9. I could not time the T4 press (no GPU here); CPU is about 3 minutes for `medium.en` and about 1 minute for `small.en`.

Single points of failure: Colab availability and a T4 quota; the runtime idling out, which wipes the preload and may wipe the uploaded zip; the zip upload; mic permission and room acoustics (untested live path); projector audio for the backup and the Kahoot clips (nothing in the notebook plays the backup WAV, F5); and no Whisper-free fallback inside the notebook. The existing laptop fallback needs a local Python environment, which the page describes but does not check.

The Sure. exchange does set up the story as written on the page: they get it "because they remember the line before", then "Today we teach a computer to do that". The model's own confused second "Sure." is reported honestly, and F4 and F8 can turn it into the lesson for blocks 6-9 instead of leaving it behind.
